# L1 — Messages: design

> Status: draft (scope checked; awaiting approval)

## Goal
A command line program that sends one prompt to Claude and prints the answer, followed by the response metadata, so I can see what a model API request and response look like.

## Scope
- In:
  - "I will start simple and just have the command line script accept one argument in quotes as the prompt that the user wants to ask the LLM."
  - "To keep things simple, I will have the script print the output to the terminal, and after the LLM response, have the effort, tokens used, and metrics that the API response exposes printed out for visibility."
  - "I want to print the approximate cost of making the query, and the latency by having a start and stop (for non streaming setting that we are working on for this lab)."
  - "Once I have a simple command line program built that fully prints out the model response with the metadata from the API response, I will then work on streaming the answer and structured JSON output."
- Out (and saved for later): conversation history / multi-turn (Phase 2), tools (L2).

## How I think it works
My guesses before building:

- **What is sent in each request?** "I don't know about the API request body shape. I guess information like the prompt, model name, system prompt, effort, will be attributes in the API request body."
- **What comes back?** "I don't know what API response shape looks like."
- **Does a second call remember the first?** "I don't think the 2nd call will remember the first call without the 2nd call passing in the 1st response as context to the 2nd call input."
- **What makes the model stop?** "After the first response is returned, I think the model stops. I actually don't understand what makes the model stop question really means."
- **What changes between low and high effort?** "The latency time will change between the low and high effort."

```
user (prompt as CLI argument) → script → Claude API → response → script prints answer, then metadata, cost, latency
```

## Components
| Piece | Responsibility |
|---|---|
| CLI script | Accepts one quoted prompt argument and an optional effort flag |
| API call | Sends the request to Claude (non-streaming for step 1) |
| Output | Prints the answer, then the response metadata, tokens used, approximate cost, and latency |

## Step 2 — Streaming

**Problem:** the program shows nothing until the whole response is finished (6s for a simple question, 22s for a hard one). Make the answer appear on screen while the model is still writing it.

### Design
1. **Replace or add?** "replace. as streaming is the standard way to see agent outputs."
2. **The thinking gap:** "During long thinking, have a temporary text printed in the terminal "Thinking.." that disappears once streamed outputs come from the API."
3. **Metadata:** "Program should print the response metadata block at the end."
4. **Which latency?** "New latency to mesure is time to first answer text."
5. **Ctrl-C:** "I anticipate the stream response will be cut off as the terminal program exits."

### How I think it works
- **What arrives over the network?** "I think HTTP Event stream arrives over the network. Not sure about the output shape of the event stream response."
- **Does it cost more or generate faster?** "I don't think streaming changes overall cost. It is an user experience improvement that makes the user feel things are faster without having to wait for the full output to be generated by the model."
- **Time to first answer text on the hard question:** "I think for the hard question, it will be a few seconds (single digit) before the first text appears."

### Refinement (after building)
- Show the model's thinking instead of only "Thinking...": request `display: "summarized"` and stream the thinking summary (faint text) before the answer. "Thinking..." stays until the first thinking or answer text arrives.

## Step 3 — Structured JSON output

**Problem:** the answer is free-form markdown, written for a person. Programs need answers with known fields they can read, store, or pass on. Make the model return its answer as JSON matching a shape I define.

### Design
1. **The shape (first idea):** "I want fields of "prompt", "output" (containing the answer text), both string type, the response metadata: (json type). I'm sure more standard JSON schema is available for a standard conversational agent, but I'm not sure what the standard is. This is just my guess."
   - **Model schema (final):** "Have the structured response schema for the model be "TLDR": string type as a summary, "Original": String with the models output."
   - `prompt` and the response metadata are added by the program, not the model (the model can't know the metadata while it's writing).
2. **Always or optional?** "JSON is always passed to the model now to build a use case of saving the typed output to a DB for persistence story."
3. **Streaming and JSON:** "In the terminal, stream the output as before. I don't think the response JSON has a streaming concept, so output typed schema has to wait for the full model response, otherwise the JSON attributes will have to keep on updating."
4. **Using the result:** "For now, just print the JSON in a prettify way."

### How I think it works
- **Does the output always match the schema?** "My guesses are that the model has some output schema field and will try to fit the output response in the format the caller specifies. I don't think it can return JSON that doesn't match. I think this part is deterministic."
- **Token cost:** "I think JSON output will cost more tokens as there is additional work needed to be done by the model."
- **Thinking:** "Yes, thinking still happens with JSON output for the model to answer harder questions."
